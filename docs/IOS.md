# The iOS app

guitarRot ships on the App Store from the same web code as the website and the
Android app: `ios/` is a Capacitor 8 project that wraps the Vite build (`dist/`) in a
`WKWebView`. There is no CocoaPods: every native piece comes in through Swift Package
Manager, which Capacitor 8 sets up by default.

## What is in the project

| Setting | Value | Where | Why |
|---|---|---|---|
| Bundle id | `com.guitarrot.app` | `project.pbxproj` | The same id as the Android application id |
| Deployment target | iOS 16.4 | `project.pbxproj` | Tailwind v4 needs Safari 16.4 (cascade layers, `@property`, `color-mix`) |
| Devices | iPhone only (`TARGETED_DEVICE_FAMILY = 1`) | `project.pbxproj` | The layout is a phone layout; iPad would need its own design pass, screenshots and review. Change it only when that exists |
| Orientation | Portrait only | `Info.plist` | Android is portrait only |
| Status bar | Light content on the `#0b0b0f` ground | `Info.plist` (`UIStatusBarStyle`) and `SystemBars` / `StatusBar` in the app | Dark ground, light icons |
| Versions | `MARKETING_VERSION` = `package.json` version, `CURRENT_PROJECT_VERSION` = Android `versionCode` | `scripts/ios-version.mjs` | One bump covers both stores, see [Versions](#versions) |
| Microphone text | "guitarRot listens to work out which note you are playing; the sound is analysed on your device and is never recorded or sent." | `Info.plist` (`NSMicrophoneUsageDescription`) | The tuner and the "play this note" checks |
| Export compliance | `ITSAppUsesNonExemptEncryption` = NO | `Info.plist` | Only HTTPS (exempt); App Store Connect does not ask per upload |
| Analytics | Collection off until the player agrees; no ad personalisation, ad storage, ad user data, ad network registration or vendor id; no automatic screen events | `Info.plist` (`FIREBASE_ANALYTICS_COLLECTION_ENABLED` and the keys beside it) | Mirrors `AndroidManifest.xml`; the app turns collection on (`src/cloud/analyticsBackend.ts`) |
| No advertising identifier | The `AnalyticsWithoutAdIdSupport` package trait | `capacitor.config.ts` (`experimental.ios.spm`) | The built app links `GoogleAppMeasurement` only, never `GoogleAppMeasurementIdentitySupport` or `AdSupport`, so there is no IDFA code and **no App Tracking Transparency prompt** |
| No Facebook SDK | The `Google` trait only for `@capacitor-firebase/authentication` | `capacitor.config.ts` | The plugin links Facebook's SDK by default; the app never uses it |
| Privacy manifest | No tracking, no tracking domains, the collected data types of [App Store Connect answers](#app-store-connect-answers), UserDefaults (CA92.1) | `ios/App/App/PrivacyInfo.xcprivacy` | Required since 2024; the SDKs inside carry their own |
| Sign in with Apple | The capability | `ios/App/App/App.entitlements` | App Store rule 4.8 |
| Firebase | Configured in `AppDelegate` only if `GoogleService-Info.plist` is in the app | `ios/App/App/AppDelegate.swift` | Without it the app is the offline app and cloud is off |
| Audio session | `playAndRecord` with `defaultToSpeaker`, `allowBluetoothA2DP`, `mixWithOthers` | `AppDelegate.swift` | See [Sound and the microphone](#sound-and-the-microphone) |

The project is Capacitor's stock one plus those changes: scene based (`SceneDelegate`,
which forwards URLs and universal links to the plugins), `CapApp-SPM/Package.swift` written
by `cap sync` (do not edit it), and `public/`, `capacitor.config.json` and `config.xml`
inside `ios/App/App/` generated by `cap sync` and git-ignored. The links `cap sync` makes in
`CapApp-SPM/symlinks/` point at your `node_modules` with absolute paths, so they are
git-ignored too. `Package.resolved` is committed: it pins `firebase-ios-sdk` (12.19.3 when
this was written) so a build next year is the build that was tested.

## Build and run

You need Xcode 16.3 or newer (the package traits need Swift tools 6.1) and the usual
`npm ci`. No CocoaPods, no `pod install`.

```bash
npm run build
npx cap sync ios            # copies dist/ in, rewrites CapApp-SPM/Package.swift
open ios/App/App.xcodeproj  # pick an iPhone simulator, press Run
```

From the command line, for a simulator (no signing needed there):

```bash
xcodebuild -project ios/App/App.xcodeproj -scheme App -configuration Debug \
  -sdk iphonesimulator -destination 'generic/platform=iOS Simulator' \
  -derivedDataPath /tmp/guitarrot-dd CODE_SIGNING_ALLOWED=NO build

xcrun simctl boot "iPhone 15 Pro"      # or a UDID from: xcrun simctl list devices
xcrun simctl install booted /tmp/guitarrot-dd/Build/Products/Debug-iphonesimulator/App.app
xcrun simctl launch booted com.guitarrot.app
xcrun simctl io booted screenshot shot.png
```

Several runtimes can be installed side by side (an iOS 17 and an iOS 27 one here), so
`-destination 'platform=iOS Simulator,name=...'` may say no device matches: use the generic
destination above, or `id=<UDID>`. A runtime's first launch can take 20 seconds.

**The cloud features need the same environment variables as the web build**
(`VITE_FIREBASE_*`, see [`ACCOUNTS.md`](ACCOUNTS.md#environment-variables)) in `.env.local`
before `npm run build`; without them the app is the offline app on iOS too, with no account
UI. Build, then `cap sync ios`, every time: a stale sync ships old web code in a new app.

Debug builds print the audio route to the console (`[guitarRot] Audio: ... to Speaker`);
in Console.app or `log show` search for `[guitarRot]`.

An unsigned simulator build logs `FirebaseAuth ... Error loading saved user ... 17995`:
that is the keychain, which an unsigned build does not have. The app does not use Firebase's
native Auth (the web SDK signs in), so it is harmless there and does not happen in a signed
build.

## Versions

`MARKETING_VERSION` (what people see) is `version` in `package.json`;
`CURRENT_PROJECT_VERSION` (the build number, which must rise with every upload) is
`versionCode` in `android/app/build.gradle`. Android's number only ever goes up, so reusing it
keeps iOS rising too and a release is one bump for both stores.

```bash
node scripts/ios-version.mjs          # write both into the Xcode project
node scripts/ios-version.mjs --check  # change nothing; exit 1 if they differ
```

Run it after bumping, before archiving. If you ever need a second upload of the same
version, raise `versionCode` again: App Store Connect refuses a build number it has seen.

## Firebase on iOS

The Firebase project is `guitarrot-a27b5`. `ios/App/App/GoogleService-Info.plist` is the
file the console gives for the iOS app `com.guitarrot.app` and is part of the App target. It
identifies the project and is not a secret, like the web config; commit it.

What it does in a running app: `AppDelegate` calls `FirebaseApp.configure()` at launch
(only if the file is in the bundle), Analytics starts **with collection disabled** (checked
in the simulator: `Analytics collection disabled`), and the JS side decides the rest
(`src/cloud/*`). The two plugins also configure Firebase themselves if the file is there,
and report "Firebase was not configured" if it is not.

- **Google sign-in needs a `REVERSED_CLIENT_ID`.** A newly registered iOS app's plist has no
  `CLIENT_ID` or `REVERSED_CLIENT_ID`: they appear once Google sign-in is switched on in the
  console. **This is the state of the committed plist.** Without them tapping "Continue with
  Google" does nothing (the plugin returns without answering when there is no client id) and
  with a client id but no URL scheme in `Info.plist` Google's SDK stops the app.
- To fix it: Firebase console > Authentication > Sign-in method > Google > Enable; then Project
  settings > Your apps > the iOS app > download `GoogleService-Info.plist` again and replace
  `ios/App/App/GoogleService-Info.plist`; then run

  ```bash
  scripts/ios-google-url-scheme.sh      # copies REVERSED_CLIENT_ID into Info.plist
  ```

  It adds the scheme once (PlistBuddy, entry `com.guitarrot.google-sign-in`), updates it if
  the value changes, and says so and changes nothing when the id is not in the plist yet.
  Run it after **every** new download of the plist and before archiving. The first write
  makes PlistBuddy rewrite `Info.plist` with its keys in a different order, which is one
  harmless diff.
- The plist in the repo says `IS_ANALYTICS_ENABLED` false: it was downloaded before
  Google Analytics was linked to the iOS app. Download it again after the step above (the
  explicit `setEnabled(true)` the app makes after consent should win, but check it: see
  DebugView in [`ACCOUNTS.md`](ACCOUNTS.md#verifying-with-debugview)).
- API key restrictions: the web API key is used from `capacitor://localhost`. If you ever
  restrict it by HTTP referrer in Google Cloud, sign-in on iOS will fail.

## Sign in with Apple and Google on iOS

- **The Apple button always shows on iOS** (`appleSignInAvailable()` in
  `src/cloud/config.ts`: cloud on and either `VITE_AUTH_APPLE=1` or the platform is iOS),
  because App Store rule 4.8 asks for it beside Google. Web and Android still need the flag.
- It is the system's own sheet (`ASAuthorizationController`), which the plugin runs. Unlike
  Apple on Android, **the iOS handler honours `skipNativeAuth`**: no native Firebase user is
  created, `credential.idToken` is Apple's ID token, `credential.nonce` is the **raw** nonce
  (Apple was sent its SHA-256), and `user.displayName` is set only the first time Apple is
  authorised (later `user` is null). `src/cloud/auth.ts` signs the JS SDK in with
  `OAuthProvider('apple.com').credential({ idToken, rawNonce })` exactly as on Android, and
  the "clear the native user" step after it is a no-op here.
- Dismissing the sheet makes the plugin reject with
  `... AuthorizationError error 1001.` and no code; the sentence before the brackets is
  translated and never says "cancel". `src/cloud/errors.ts` now reads that as a cancel, so
  backing out shows nothing instead of "Something went wrong".
- Google on iOS is Google's own sign-in SDK in a system web authentication session; the plugin
  returns Google's ID token and the JS SDK signs in with it, as on Android.
- What the native flow needs in the Apple Developer account is only the **App ID with the
  Sign in with Apple capability** and, in the Firebase console, Apple enabled as a provider.
  The Services ID, the `.p8` key and the return URL of
  [`ACCOUNTS.md`](ACCOUNTS.md#manual-setup-once) are for the web and Android browser flow
  and for **revoking the token when an account is deleted** (see
  [Known gaps](#known-gaps-and-review-risks)).

## Sound and the microphone

- **Silent switch and speaker.** `AppDelegate` sets the app's audio session to
  `playAndRecord` before the web view makes a sound, with `defaultToSpeaker` (the
  loudspeaker, not the earpiece), `allowBluetoothA2DP` (headphones keep full-quality output
  while the phone's mic listens) and `mixWithOthers` (opening the app does not stop the
  player's music). Play-and-record is not muted by the ringer switch. It is set up front,
  not when the mic opens, because the tuner records while lessons play and changing the
  category then would cut the sound off.
- Checked in the simulator: the category is `PlayAndRecord` and the route is `Speaker`, a
  Web Audio context starts running by itself (Capacitor sets
  `mediaTypesRequiringUserActionForPlayback` to none) and its clock advances. **Not
  checked: the ringer switch and the real loudspeaker, which need a phone.**
- **Microphone permission.** Capacitor's `WKUIDelegate` grants `getUserMedia` itself, so the
  only prompt is the system one with the text above, shown the first time the tuner or a
  "listen for me" step asks. There is no second, WebKit prompt.
- `WKWebView` exposes `navigator.audioSession` (type `auto`). It is not used: if a phone
  turns out to mute Web Audio with the switch on, setting `navigator.audioSession.type =
  'play-and-record'` where the audio is unlocked is the next thing to try.

## Layout: safe areas, icon, launch screen

- `index.html` has `viewport-fit=cover`, and the app already pads with
  `env(safe-area-inset-*)` (top in `AppShell`, bottom in `TabBar`, sheets and lesson
  footers), the same CSS Android's `SystemBars` feeds. Nothing in the layout needed to change
  for iOS and Android's look is untouched.
- Measured in the simulator: an iPhone 15 Pro Max (Dynamic Island) reports 59 px at the top
  and 34 px at the bottom, an iPhone SE has none. **The web view reports them about a second
  after launch** (the first layout has 0), which `env()` follows by itself; the page must
  never copy an inset into JS once at start-up.
- The 1024 px App Store icon is `assets/icon-only.png` (RGB, **no alpha**, full bleed; iOS
  rounds it), as `AppIcon.appiconset/AppIcon-512@2x.png`. The launch screen is
  `assets/splash.png` on `#0b0b0f` (`LaunchScreen.storyboard`), the Android splash's art, so a
  light-mode phone never flashes white. The splash stays until the app calls
  `SplashScreen.hide()` (`launchAutoHide` is off).

## Manual steps only a person can do

Do them in this order. Nothing here can be done from the repo.

**Apple Developer account**

- [ ] Use the **Underdog Labs S.R.L.** team in the Apple Developer Program (the organisation
      membership CeFacem ships with; no new enrolment). The person who signs in needs the
      Admin or App Manager role.
- [ ] Certificates, Identifiers & Profiles > Identifiers > **+** > App IDs > App: description
      `guitarRot`, bundle id **`com.guitarrot.app`**, capability **Sign in with Apple**
      (Enable as a primary App ID). Xcode can also create it when signing is switched on, but
      then check the capability is on.
- [ ] Xcode > the App target > Signing & Capabilities: **Team = Underdog Labs S.R.L.**,
      **Automatically manage signing**. The Sign in with Apple capability is already there (from
      `App.entitlements`). Xcode writes `DEVELOPMENT_TEAM` into `project.pbxproj`: commit it.

**Firebase**

- [ ] Console > Authentication > Sign-in method: **Google** on (needed for the iOS client id),
      **Apple** on.
- [ ] Apple provider: for the native iOS flow nothing more is needed to sign in. To revoke
      tokens on account deletion (see [Known gaps](#known-gaps-and-review-risks)) fill in the
      Apple team id, key id and `.p8` as in [`ACCOUNTS.md`](ACCOUNTS.md#apple-sign-in-optional)
      steps 3 and 5 to 6 (the Services ID is for the web).
- [ ] Download `GoogleService-Info.plist` again (Project settings > Your apps > iOS), replace
      `ios/App/App/GoogleService-Info.plist`, run `scripts/ios-google-url-scheme.sh`, commit both.
      Repeat whenever you change a sign-in method or link Analytics.

**App Store Connect**

- [ ] Apps > **+** > New app: platform iOS; name `guitarRot: Learn Guitar` (30 characters at
      most; the name is the same as the Play listing); primary language English (U.S.); bundle id
      `com.guitarrot.app`; **SKU** `guitarrot-ios` (never shown; cannot change); user access Full.
- [ ] App Information: **Category Education** (secondary Music if you want one); content rights:
      the app does not use third-party content (all music and tab are original, see the content
      policy in the README); privacy policy URL `https://guitar-rot.vercel.app/privacy.html`;
      support URL `https://guitar-rot.vercel.app`; contact `guitar.rot@proton.me`.
- [ ] Pricing and availability: free, all countries you want (the policy and terms are written for
      the EU and Romania, so check the regions you pick).
- [ ] App Privacy: the [labels below](#app-privacy-nutrition-labels), then **Publish**.
- [ ] Age rating: the [answers below](#age-rating).
- [ ] The version page: description and keywords (the Play text in `store/listing.md` is the
      base; drop "No account. No ads. No tracking." as `ACCOUNTS.md` says), screenshots (see
      [below](#screenshots)), the build (after the first upload), version `1.2.0` or the current one.
- [ ] App Review information: no sign-in is needed (every lesson works without an account); say
      that an account is optional, that **Sign in with Apple** and Google are offered, that the
      tuner and the "play this note" checks use the microphone (analysed on the device, never
      recorded), and that **Delete account** is in Settings > Account. Give the contact above.

**Archive, test, submit**

- [ ] `npm run build && npx cap sync ios && node scripts/ios-version.mjs` (with `.env.local` set).
- [ ] Xcode > Product > Destination **Any iOS Device (arm64)** > Product > **Archive**.
- [ ] Organizer > **Distribute App** > App Store Connect > Upload. Fix whatever the validation
      says (see [Known gaps](#known-gaps-and-review-risks) for the ones to expect).
- [ ] App Store Connect > TestFlight: wait for processing, add yourself as an internal tester,
      install on a phone and run the [phone checklist](#phone-checklist) below.
- [ ] Select the build on the version page, **Add for Review**, **Submit**.

## App Store Connect answers

### App Privacy (nutrition labels)

Derived from [`public/privacy.html`](../public/privacy.html), the events in
[`ACCOUNTS.md`](ACCOUNTS.md#what-is-tracked) and the Play Data safety table beside them.
`ios/App/App/PrivacyInfo.xcprivacy` declares the same.

**Do you or your third-party partners collect data from this app?** Yes (Firebase is our
processor, and what it handles counts as collected).

**Data linked to the user** (only for somebody who made an account; all for **App
functionality**; none used for tracking):

| Category > type | What it is |
|---|---|
| Contact info > **Email address** | the account's email |
| Contact info > **Name** | the name Google or Apple shares, and the display name |
| Identifiers > **User ID** | the Firebase uid, and the username (public: the leaderboard) |
| User content > **Gameplay content** | the synced progress (lessons, points, streaks, quiz bests, settings) and the leaderboard entry |

**Data not linked to the user** (only for somebody who answered yes to "Share anonymous
usage"; purpose **Analytics**; none used for tracking): it is tied to a random id on the
device, never to the account (no `user_id` is ever sent):

| Category > type | What it is |
|---|---|
| Usage data > **Product interaction** | the screens opened and the features used (the events in `ACCOUNTS.md`) |
| Identifiers > **Device ID** | Firebase's random app-instance id (no advertising id, and the vendor id is switched off) |
| Location > **Coarse location** | Google Analytics works out country and city from the connection |

**Not collected:** diagnostics and crash data, purchases, financial info, health, contacts,
browsing and search history, sensitive info, **audio data** (the microphone is analysed on
the device and never recorded or sent, which Apple does not count as collection), photos (a
Google profile picture is only a link shown in the app; if you want to be stricter than the
Play form, tick Photos or videos as well).

**Data used to track you: none.** Tracking = No, no tracking domains, no ATT prompt.

If App Review asks why Device ID is "not linked": it is a random per-install id, never
combined with the account, and the person can switch it off and have it removed in Settings.
The cautious alternative is to declare Device ID as linked; declaring more is never a
rejection, declaring less can be.

### Age rating

Apple's questionnaire has changed several times; these are the intended answers, so read what
the form asks and keep to them.

| Question | Answer |
|---|---|
| Parental controls, age assurance | No |
| Unrestricted web access | No (Settings links open the policy in the browser; there is no browser in the app) |
| **User-generated content** | **Yes**: usernames and leaderboard names are public text typed by players (filtered, reportable, hideable; see [Moderation in `ACCOUNTS.md`](ACCOUNTS.md#moderation)). The Play answer is the same ("users interact") |
| Messaging and chat | No |
| Advertising | No |
| Medical or wellness, sexual content or nudity, violence, profanity or crude humour, horror, alcohol, tobacco or drugs, gambling, contests, simulated gambling | None / No |

Expect a low rating (4+ or 9+ depending on how the form scores user-generated names). The
Play target audience is 13 and over and the policy asks under-16s to ask a parent before
making an account; the App Store rating does not replace that.

### Export compliance

None beyond exempt encryption (HTTPS, the system's). `ITSAppUsesNonExemptEncryption` is
NO in `Info.plist`, so App Store Connect does not ask when you upload. If it asks anyway:
the app uses encryption only for authentication and HTTPS through the operating system and
Google's SDKs, which is exempt; no export compliance document is needed.

### Screenshots

iPhone only, so **no iPad screenshots**. The slots to fill are **6.9"** and **6.5"** (a 6.1"
set is optional; smaller sizes are scaled from the largest given). Portrait, no alpha. App
Store Connect lists the exact pixel sizes it accepts for each slot; when this was written:

| Slot | Size | Simulator that gives it |
|---|---|---|
| 6.9" | 1320 x 2868 (or 1290 x 2796) | iPhone 17 or 18 Pro Max (1320 x 2868), iPhone 15 Pro Max (1290 x 2796) |
| 6.5" | 1284 x 2778 (or 1242 x 2688) | iPhone 15 Plus (1284 x 2778) |

`xcrun simctl io booted screenshot name.png` writes them at the right size. The Android
screenshots (1080 x 2160) cannot be reused. Use a build with the account features on if the
screenshots should show them.

## Known gaps and review risks

In order of how likely each is to hold up a review.

1. **Apple token revocation on account deletion is not implemented.** Guideline 5.1.1(v): an
   app that offers account creation with Sign in with Apple must revoke the Apple token when the
   account is deleted (the account deletion itself, in Settings, exists and works). `ACCOUNTS.md`
   already notes it. What it needs, and why it was not guessed at without a real Apple
   account: Apple's authorization code (one use, a few minutes of life) and a native Firebase
   user, because the plugin's `revokeAccessToken` calls `Auth.revokeToken(withAuthorizationCode:)`,
   which asks the native SDK's current user for its ID token and the app deliberately has none
   (`skipNativeAuth`). The plan: on iOS, for an account with an `apple.com` provider,
   `deleteAccount` runs the Apple sheet once with `signInWithApple({ skipNativeAuth: false })`,
   uses its `idToken` and nonce for the JS re-authentication, calls
   `FirebaseAuthentication.revokeAccessToken({ token: credential.authorizationCode })`, then signs
   the native user out; if revoking fails it must not stop the deletion. It also needs the
   Apple team id, key id and `.p8` filled in under Firebase's Apple provider (step 6 of
   [`ACCOUNTS.md`](ACCOUNTS.md#manual-setup-once)). It cannot be tested without them and a phone.
2. **Google sign-in is not usable until the plist has a client id** (see
   [Firebase on iOS](#firebase-on-ios)). Until then, tapping the button does nothing.
3. **The plugin links `AppTrackingTransparency`.** `@capacitor-firebase/authentication` imports it
   for a helper the app never calls, so the binary references `requestTrackingAuthorization` and
   App Store Connect may e-mail a missing-purpose-string warning (ITMS-90683,
   `NSUserTrackingUsageDescription`) after an upload. The app never shows the prompt and does not
   track; a warning is not a rejection, and the answer is that the code is unused. Do **not** add
   the usage string just to quiet it unless Review asks.
4. **Names shown to other players** need the filter, the report and the hide that `ACCOUNTS.md`
   describes (guideline 1.2); they exist. The filter is on the phone only.
5. **Not tried with a real Apple or Google account:** neither sign-in has been run end to end.
   Both go through code that is covered by unit tests with the plugin stood in for.
6. **The privacy page** says what the iPhone app does (iCloud backup, no ads), and the labels
   above match it; re-read both whenever the data the app collects changes.

## What was checked, and what was not

Checked, on an iPhone SE (3rd generation, iOS 17.2), an iPhone 15 Pro Max (iOS 17.2) and an
iPhone 18 Pro (iOS 27.0) in the simulator:

- The app builds (`BUILD SUCCEEDED`, Xcode 27) and launches with Firebase configured; the log
  shows `Analytics v.12.19.3 started` and `Analytics collection disabled`.
- With the plist missing, a build logs "Firebase is off" and runs (the guard).
- The start screen is clear of the status bar and the Dynamic Island, with light status bar
  content, on all three.
- The audio session is `PlayAndRecord` to `Speaker`; a Web Audio context runs and its clock
  advances with no gesture; `navigator.audioSession` and `getUserMedia` exist.
- Safe-area insets are 59 / 34 px on the Pro Max and 0 on the SE.
- The built app contains `PrivacyInfo.xcprivacy`, `GoogleService-Info.plist` and the Info.plist
  keys above, links no advertising-identifier code, and `scripts/ios-google-url-scheme.sh` adds,
  keeps and updates its entry correctly on a copy of `Info.plist`.
- `npx vitest run` and `npx tsc -b` are green.

Not checked, because it needs a phone, a real account, or a tap the headless simulator could
not make here:

- Anything past the start screen (the feed, the tab bar over the home indicator, the tuner
  screen), and the microphone prompt: in the headless simulator `getUserMedia` stayed pending
  without showing the prompt. The prompt text, the plist key and Capacitor's grant of
  `getUserMedia` are as described above; the [phone checklist](#phone-checklist) covers it.
- The ringer switch, the real loudspeaker, Bluetooth, interruptions (a call).
- Sign in with Apple and with Google, account deletion, token revocation, analytics reaching
  DebugView, archive and upload, TestFlight.
